# Decision log

| Date | Decision | Why |
|---|---|---|
| 2026-07-14 | Rust core owns all domain/DB logic; React is thin | Integrity at the DB; one implementation; cargo-testable (spec ADR 1) |
| 2026-07-14 | Quantities: fixed-point integer x1000 | Exact; continuous units supported (spec ADR 4) |
| 2026-07-14 | ULIDs for IDs | Stable, sortable, deterministic exports (spec ADR 5) |
| 2026-07-14 | `PRAGMA user_version` + embedded numbered SQL migrations | Minimal, transactional, testable |
| 2026-07-14 | Redaction at the log-writer layer | Secrets cannot reach disk regardless of call site |
| 2026-07-14 | Hand-written TS bindings for the single Phase 1 command | tauri-specta adopted in Phase 2 when the command surface grows (spec ADR 11) |
| 2026-07-14 | TanStack Router deferred to Phase 3 | Phase 1 has one screen; YAGNI |
| 2026-07-14 | rusqlite backup feature + validated serde deserialization for Quantity | Review findings during Tasks 4-5 (see .superpowers/sdd reports) |
| 2026-07-14 | Web app uses Vite appType 'mpa' | Preview SPA fallback masked missing-snapshot 404; forward risk documented in vite.config.ts |
| 2026-07-14 | Phase 2 split into 2a (schema+ledger), 2b (categories/attributes/units/dimensions), 2c (search+matching+commands) | Keeps each plan reviewable; each ships working software |
| 2026-07-14 | Adjustments never touch lifetime counters and require a note | They are corrections, not history |
| 2026-07-14 | Archived parts allow only release/return/reversal | Stock must drain home without reactivating the part |
| 2026-07-14 | Reversal deltas recomputed from stored rows (`delta_from_stored`) | One source of truth shared by reversals and the validator |
| 2026-07-14 | Group members ordered by rowid | created_at is second-granular; ULIDs don't sort by creation time |
| 2026-07-14 | Group members cannot be reversed individually | Preserves atomic group reversibility; compensating ops cover line-level corrections |
| 2026-07-14 | Layer-1 SQL defense is CHECK constraints only (no verification triggers, deviating from spec §4.5) | Domain layer is the only writer; triggers add complexity without a second writer. Revisit if another writer appears |
| 2026-07-14 | Attribute normalization stores f64 for filtering; identity compares exact (mantissa, exp10) re-parsed from original text | No float-equality traps; original text is never lost |
| 2026-07-14 | Built-in seeds are insert-only with deterministic ids, run at every open | User customizations survive; new built-ins arrive in upgrades |
| 2026-07-14 | Bare chip package codes read as imperial (0603 = imperial unless 'metric' suffix) | Matches supplier convention |
| 2026-07-14 | Curated attribute sets for 17 key categories; others get shared basics | Full 70-category curation is data work that can grow incrementally |
| 2026-07-14 | quantity_unit changes blocked once a part has transactions | Stored milli values would silently change meaning |
| 2026-07-16 | Duplicate-matching identity comparison is exact-form (`ParsedValue`/package-canonical/trimmed text), never `f64` | Lossy float equality is unsound for "10k == 10000 ohm"; reuses the units engine's own exact comparable form |
| 2026-07-16 | Only a fixed list of seeded PASSIVE categories (Resistor, Capacitor, Inductor, Resistor network, Ferrite bead, Crystal) auto-combine on an exact identity match; every other category, including all custom ones, caps at `ProbableEquivalent` | Spec: never silently merge actives/ICs; passives are safe to fungibly combine, actives are not |
| 2026-07-16 | `search_text` is a single denormalized per-part choke-point rebuilt by `refresh_search_text`, kept in sync with an FTS5 external-content `parts_fts` index by triggers | One place knows how to build searchable content; FTS index stays consistent without duplicating part data |
| 2026-07-16 | `has:footprint` returns a typed `UnsupportedSearchKey`, not `UnknownSearchKey` or an empty result | Footprint/CAD-link data is a real, recognized concept just not modeled until Phase 3 — distinguishes "not yet" from "not a thing" |
| 2026-07-16 | Pinned specta 2.0.0-rc.25 / tauri-specta 2.0.0-rc.25 / specta-typescript 0.0.12 (the upstream-recommended matched set); i64 fields export as JS `number` via `dangerously_cast_bigints_to_number` | Reproducible generated bindings; all i64 values (milli-quantities, micro-prices) stay far under 2^53 in any realistic inventory |
| 2026-07-16 | `CommandError { code, message }`: `code` is the snake_case `DbError` variant name, `message` is its `Display` text (never `Debug`) | Stable, matchable-by-frontend error codes; `Debug` text is for logs, not UI |
| 2026-07-16 | Search attribute filters require the exact attribute key (e.g. `voltage_rating:`, not `voltage:`); no label/alias resolution yet | Safer to require exactness than guess a match; friendlier key resolution arrives Phase 3 |
| 2026-07-17 | The desktop UI calls ONLY the generated typed `commands.*` (`bindings.gen.ts`), never raw `invoke`; a drift-detecting `export_bindings` test (run with the env unset in the gate) fails if the committed bindings and the command surface disagree | One typed contract the compiler and the gate both enforce; the UI can't call a command that doesn't exist or drift from its signature |
| 2026-07-17 | Part-create is non-atomic: the form issues sequential mutations (`create_part`, then per-attribute `set_attribute`, dimensions, variants), combined into one toast; a failed later step leaves a partial part | Ships the category-adaptive form in Phase 3 without a bespoke batched command; a future `create_part_full` batched command is the clean fix (noted as a known limitation) |
| 2026-07-17 | Merge/split of canonical parts: Phase 3 exposes matching *suggestions* + mark-not-equivalent (`record_equivalence`); the merge/split *executor* is deferred to Phase 7 | The executor rewrites history and needs the safety-backup infra Phase 7 brings; suggesting/flagging is safe now, destructively merging is not |
| 2026-07-17 | Dashboard reads aggregate commands (`dashboard_summary`, `recent_transactions`) instead of computing counts client-side from N per-part queries | One cheap server round-trip vs. fetching every part to sum it in JS; the Rust core already owns stock math |
| 2026-07-17 | Attachments are content-addressed (SHA-256): identical bytes stored once (file name + PK both derive from content); orphan-blob GC deferred to Phase 7 | Free deduplication and a stable name; removing a link can't safely delete a shared blob, and reference-counted GC is Phase 7 backup-adjacent work |
| 2026-07-17 | Caller-supplied attachment extensions pass a strict `[a-z0-9]{1,16}` whitelist (`sanitize_ext`) before joining the on-disk path | The only check between the `add_attachment` command and the filesystem; a `[a-z0-9]` whitelist cannot encode `/`, `\`, or `..`, so no value can escape the attachments dir (path-traversal safety) |
| 2026-07-17 | `dev_seed` is one entry in the single `collect_commands!` list for every build profile, with a `#[cfg(debug_assertions)]` real body and a `#[cfg(not)]` release stub that errors | Body-gating (not entry-gating) keeps the drift test covering it, and keeps release binaries' command list identical, while the seed can never run against a production DB |
| 2026-07-17 | CSP gains `img-src 'self' blob:` (`tauri.conf.json`) | Attachment image thumbnails are rendered from in-memory `blob:` URLs; the default `img-src 'self'` would block them |
| 2026-07-17 | BOM line `reserved`/`consumed` are derived from the ledger on every read (`derive_reserved_consumed`, `bom.rs`), never stored counters | Same source of truth `validate.rs` already reconciles `part_stock` from; a second stored counter could drift from the append-only ledger |
| 2026-07-17 | Build-from-BOM (`reserve_bom`/`release_bom_reservations`/`build_from_bom`) computes a `Vec<LedgerOp>` and applies it through the existing Phase 2a `apply_group` as one atomic all-or-nothing group, rather than a parallel transaction path | Reuses tested atomicity/reversal machinery; an approved available-draw line that turns out short fails the whole group via the same `part_stock` CHECK constraint that already gates every other op |
| 2026-07-17 | A successful `build_from_bom` auto-activates a `planned` project (no-op if already `active`/`completed`/`archived`); a failed build never touches project status | Starting a build is the natural signal a `planned` project has begun; the group's atomicity means status only advances when the build actually committed |
| 2026-07-17 | `transactions.bom_item_id` (added FK-less in migration 0002) stays without a database-level foreign key; `bom.rs` derives reserved/consumed by `(project_id, part_id)` instead of `bom_item_id` | SQLite can't add an FK to an existing column of an already-STRICT table without a full rebuild, and only the domain layer ever writes to the append-only ledger — a DB-level FK would only catch a domain bug, never bad input. `bom_items.UNIQUE(project_id, part_id)` makes the `(project_id, part_id)` key exactly equivalent to `bom_item_id` for this schema, so no attribution is lost |
| 2026-07-18 | PDF row/column reconstruction is driven by a `PdfTextSource` abstraction, unit-tested against a committed positioned-token JSON fixture rather than a live extraction | `pdfium-render` needs a native DLL unavailable in this dev/CI environment; mirrors the units-engine shared-fixture pattern so reconstruction logic stays fast and hermetic to test |
| 2026-07-18 | Import money is stored as `*_micros` (i64) and quantities as `*_milli` (i64), never a float, throughout `inventory-import`/`import_lines`/`price_history` | DigiKey unit prices carry up to 5 fractional digits (`1.82000`) a float would round; matches the existing `part_stock`/`transactions` fixed-point convention |
| 2026-07-18 | A PDF `TARIFF` sub-row becomes its own `LineKind::Tariff` `ParsedLine` (joined to its part by matching `line_number`), rather than adding a per-line tariff field to `ParsedLine` | Keeps the `ParsedLine` model the single vocabulary every parser (CSV/XLSX/PDF) shares without an unmodeled field only PDF would ever populate; 5b already keys everything off `line_number` |
| 2026-07-18 | PDF text extraction happens via `pdfium-render` at runtime, but the committed test fixture was generated via PyMuPDF (`samples/digikey/tools/dump_tokens.py`), a different library | No `pdfium.dll` is available on the authoring/CI machine; both libraries' word extraction normalizes to the same top-left/y-down/points convention, so the fixture is interchangeable with a live pdfium extraction for reconstruction-logic testing purposes |
| 2026-07-18 | DigiKey sample PII handling: raw supplier files stay in a gitignored `samples/digikey/private/`, only hand-sanitized fixtures are committed, and a guard test (`no_pii.rs`) fails if a denylisted personal string appears in any committed fixture | The real sample invoice carries a real name/address/account number (spec §21 decision #10); sanitize-at-source plus an automated denylist scan is cheaper and more reliable than trusting manual redaction alone |
| 2026-07-18 | A scanned/image-only PDF (extraction yields ~no positioned tokens) is detected by a token-count heuristic and produces a `ParsedInvoice` with no fabricated data plus a warning; real OCR is deferred past Phase 5a | 5d's manual-correction UI needs a defined, low-confidence signal to build against now; implementing actual OCR (Windows OCR APIs) is separable work that shouldn't block 5a's Upload→Extract scope |
| 2026-07-18 | `commit_import` applies every part/variant/listing creation, receive, price-history write, and alias insert for an entire import as ONE `rusqlite` transaction (reusing `build_group_in_tx`/the new in-tx part/variant/listing helpers), rather than a sequence of independent writes | No partial state if a later line fails — the import stays `parsed` and nothing it touched persists; fully reversible as a single group, matching the `build_from_bom` atomicity pattern |
| 2026-07-18 | Only `LineKind::Part` lines may ever create a part or a receive — `commit_import` rejects an `AddStock`/`CreateNew`/`AddAsVariant` decision keyed to a `fee`/`tariff`/`no_charge`/`unknown` line (`DbError::NonPartLineNotReceivable`) before mutating anything | Spec §10's hard rule against phantom inventory from tariff/fee rows must hold even if a caller ignores the review's advisory `ProposedAction::NonInventory` default — enforcing it in `commit_import` itself, not just the review layer, is the only place a bad decision can't slip through |
| 2026-07-18 | `commit_import` always receives the line's SHIPPED quantity, never ordered (`shipped_milli`, not `ordered_milli`) — a zero/absent-shipped (fully backordered) line creates no receive at all, though its part/variant/listing is still created at zero stock | Matches what physically arrived; ordered-but-not-shipped stock doesn't exist yet, and double-counting a later shipment of the same order is avoided by receiving only what each import's lines actually shipped |
| 2026-07-18 | Matching decisions are recorded as `part_aliases` at commit time (`INSERT OR IGNORE` on the line's supplier_sku/mpn → resolved part_id, source `import`), tolerating a duplicate rather than erroring like the public `add_alias`'s `AliasTaken` | A repeat import of the same SKU should resolve to `KnownAlias` next time without user re-confirmation (the matching-memory loop spec §10 wants); first-writer-wins on a collision is fine because the point is only that a known value be *recognized*, not that this insert be authoritative |
| 2026-07-18 | `reverse_import` returns stock to its pre-import level (via `reverse_group`) but never deletes the parts/variants/listings a commit created — they simply end up at zero stock | Matches the system's existing "history is never deleted" rule (identical to why archived parts and reversed transactions are never dropped); a part with a reversed import can still show its price history and be received against again later |
| 2026-07-18 | A commit whose every decided line is `Skip`ped or fully backordered (no receive ops at all) still succeeds — it creates parts with no stock, sets `imports.commit_group_id` to NULL, and returns a synthetic never-persisted `GroupRecord` instead of surfacing `DbError::EmptyGroup` | Unlike `apply_group`'s public entry point, an all-backordered import is a completely valid outcome (a part still gets filed for a later shipment), so this edge case must not be treated as a failure; `reverse_import` on a NULL `commit_group_id` symmetrically only flips status, nothing to reverse |
| 2026-07-18 | Enrichment provider chain runs DigiKey Product Information V4 (authoritative supplier catalog) first, the offline description parser (always available, never fabricates) last; `run_chain` merges first-seen-key-wins | A configured, authoritative source should win over a shorthand guess for the same field; the always-on fallback means a part still gets category/package/attribute candidates with zero network or configuration |
| 2026-07-18 | DigiKey Client ID/Secret and the OAuth access token live ONLY in the OS credential store (`keyring`, Windows Credential Manager) or in-memory — never SQLite, `settings`, logs, exports, or a fixture; `get_digikey_status` returns a `bool` + environment string, never the secret | Spec §16/ADR #3: a credential leak into a backed-up DB, a log file, or an exported snapshot would be far harder to contain than one confined to the OS's own secret store |
| 2026-07-18 | Per-field provenance (migration 0009) drives a trust rule: a field currently sourced `manual` is never auto-overwritten (surfaced for review instead); an `inferred` candidate overwriting ANY existing value (even one with no recorded provenance) also requires review; `apply_enrichment` only ever writes fields the caller explicitly approved | Spec §5/§11: a human-confirmed value must never be silently clobbered by an automated guess, and a low-confidence guess must never silently replace something already on file, confirmed or not — simpler and strictly more conservative than consulting each category's identity-attribute flags |
| 2026-07-18 | The DigiKey client's on-disk response cache (`<cache_dir>/digikey/<key>.json`, keyed by the sanitized/uppercased MPN or supplier SKU) is checked BEFORE credentials are loaded | A part whose response was already fetched still enriches even if credentials are later cleared, and makes the cache-hit tests hermetic (no credential store touched at all, mocked or real) — never contains a secret, since only the raw product JSON is cached |
| 2026-07-18 | DigiKey sandbox vs production is a non-secret `settings` key (`digikey_environment`), defaulting to `sandbox` whenever unset or unrecognized; the same credentials work against both, only the base URL differs | A corrupted or missing setting must never silently start talking to the real production API; sandbox-by-default is the safe failure mode (confirmed by live verification — see `docs/enrichment.md` — that the user's production-only DigiKey app 401s against the sandbox base URL, so the toggle is not merely cosmetic) |
